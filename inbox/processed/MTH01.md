# 1. Objet

Le present document definit la methode RHYAD appliquee aux missions de programmation, d'assistance a maitrise d'ouvrage (AMO) et de conception de projets industriels.

Il decrit les principes methodologiques, les regles documentaires et les processus de travail permettant de garantir la coherence, la tracabilite et la qualite des livrables.

Il constitue le referentiel commun de tous les intervenants du projet.

# 2. Domaine d'application

La methode RHYAD s'applique :

- aux etudes de programmation ;
- aux missions d'AMO ;
- aux etudes de conception ;
- aux projets industriels complexes ;
- aux projets pharmaceutiques ;
- aux futurs projets utilisant la methode RHYAD.

# 3. Philosophie RHYAD

La methode RHYAD repose sur les principes suivants :

- une information = une seule source ;
- une decision = une justification ;
- une modification = un impact documentaire identifie ;
- une variante = une analyse multicritere ;
- une exigence = un document de reference.

La methode privilegie :

- la simplicite ;
- la tracabilite ;
- la robustesse documentaire ;
- l'ingenierie collaborative ;
- l'aide a la decision.

# 5. Principes methodologiques RHYAD

## P-001 - Une information = une seule source

Chaque information est definie une seule fois.

Les autres documents y font reference.

## P-002 - Perimetre documentaire

Les documents RHYAD definissent les exigences de programmation et de conception.

Ils ne decrivent pas :

- les procedures d'exploitation ;
- les SOP ;
- les procedures de maintenance ;
- les procedures qualite de l'exploitant.

## P-003 - Justification des choix

Aucune solution technique ne peut etre retenue sans justification.

Les variantes etudiees sont documentees.

Le choix est motive.

## P-004 - Impacts documentaires

Toute modification identifie :

- les documents impactes ;
- les risques impactes ;
- les decisions impactees ;
- les actions associees.

## P-005 - Infrastructures critiques

Les infrastructures critiques sont identifiees par une analyse de risques.

Leur niveau de redondance, de disponibilite et de protection est justifie.

# 6. Processus RHYAD

Le processus RHYAD decrit le cheminement methodologique d'un projet depuis l'expression du besoin jusqu'a la remise du Dossier des Ouvrages Executes (DOE).

Chaque etape produit des livrables valides avant le passage a la suivante. Les decisions prises a chaque jalon sont enregistrees dans les registres du projet et leurs impacts documentaires sont propages dans l'ensemble du referentiel RHYAD.

## Principes transversaux du processus

Les principes suivants s'appliquent a toutes les etapes :

- Tracabilite : chaque decision est enregistree et historisee.
- Validation : aucun livrable ne passe a l'etape suivante sans validation.
- Collaboration : toutes les disciplines travaillent sur une source documentaire unique.
- Amelioration continue : les retours d'experience enrichissent la methode RHYAD.

# 7. Gestion des interfaces

Chaque document doit identifier :

- ses donnees d'entree ;
- ses donnees de sortie ;
- les documents lies ;
- les disciplines concernees ;
- les impacts documentaires.

Les interfaces entre disciplines doivent etre identifiees des les premieres phases de conception afin de limiter les incoherences techniques, les oublis et les conflits de responsabilite.

Chaque interface identifiee doit pouvoir etre tracee jusqu'aux documents concernes, aux decisions associees et, lorsque cela est pertinent, aux risques et actions du projet.

# 8. Design Drivers

Les Design Drivers representent les objectifs qui orientent la conception.

Ils sont definis avant toute etude de variantes.

Ils servent de base a l'evaluation des solutions techniques.

Chaque Design Basis definit ses Design Drivers specifiques.

Les Design Drivers peuvent notamment porter sur :

- la conformite reglementaire ;
- la qualite pharmaceutique ;
- la securite des personnes ;
- la securite des installations ;
- la continuite d'activite ;
- la disponibilite des installations ;
- la maintenabilite ;
- l'evolutivite ;
- les performances energetiques ;
- les couts d'investissement (CAPEX) ;
- les couts d'exploitation (OPEX) ;
- la durabilite ;
- les contraintes du contexte local.

Ils constituent les criteres de reference pour l'analyse multicritere des variantes.

# 9. Analyse des variantes

Toute variante est etudiee selon une methode commune.

## Etapes

1. Identification du besoin.
2. Definition des variantes.
3. Identification des Design Drivers.
4. Proposition des ponderations.
5. Validation des ponderations par le Maitre d'Ouvrage.
6. Analyse multicritere.
7. Justification du choix.
8. Enregistrement de la decision.

Chaque variante etudiee doit presenter :

- son objectif ;
- ses avantages ;
- ses inconvenients ;
- ses impacts techniques ;
- ses impacts reglementaires ;
- ses impacts economiques ;
- ses impacts sur l'exploitation ;
- ses impacts sur la maintenance ;
- ses impacts sur les performances energetiques ;
- ses impacts documentaires.

Les conclusions de l'analyse sont consignees dans les documents concernes et les decisions retenues sont enregistrees dans le Registre des Decisions.

# 10. Matrice d'aide a la decision

Les variantes sont comparees a l'aide d'une matrice multicritere.

Les criteres sont issus des Design Drivers.

Les ponderations :

- sont proposees par l'equipe projet ;
- sont validees par le Maitre d'Ouvrage ;
- peuvent varier selon le sujet etudie.

La matrice constitue un outil d'aide a la decision et ne remplace pas le jugement technique.

Les criteres peuvent notamment couvrir :

- conformite reglementaire ;
- performances techniques ;
- qualite ;
- disponibilite ;
- maintenabilite ;
- evolutivite ;
- securite ;
- cybersecurite ;
- impact environnemental ;
- CAPEX ;
- OPEX ;
- TCO ;
- consommation energetique ;
- facilite d'exploitation ;
- delai de realisation.

Les resultats de la matrice sont presentes de maniere transparente afin de justifier le choix retenu.

# 11. Gestion documentaire

Chaque document possede :

- une reference unique ;
- une version ;
- un statut documentaire ;
- un historique des revisions ;
- un responsable.

Tous les documents utilisent le modele documentaire RHYAD.

Chaque evolution documentaire est soumise a une revue puis a une validation avant diffusion.

Les documents lies sont identifies afin de garantir la coherence du referentiel documentaire.

Les livrables DOCX et PDF sont générés à partir de la source documentaire validée conformément à la méthode RHYAD.

# 12. Gestion des decisions

Toute decision :

- possede un identifiant unique ;
- est enregistree dans le Registre des Decisions ;
- reference les documents impactes ;
- est propagee dans les documents concernes.

Chaque decision comporte notamment :

- son objet ;
- son contexte ;
- sa justification ;
- son auteur ;
- son valideur ;
- sa date ;
- les documents concernes ;
- les risques concernes ;
- les actions associees ;
- les impacts documentaires.

Une decision validee devient une donnee d'entree pour les phases suivantes du projet.

# 13. Gestion des risques

Les risques :

- sont identifies dans les Donnees Techniques et dans l'ACAP ;
- sont centralises dans le Registre des Risques ;
- sont suivis jusqu'a leur cloture.

Chaque risque est :

- identifie ;
- analyse ;
- evalue ;
- traite ;
- suivi.

Les mesures de maitrise sont documentees et leur efficacite est revue aux principaux jalons du projet.

Les risques ayant un impact sur plusieurs disciplines doivent etre partages entre les equipes concernees afin de garantir une approche coherente.

# 14. Ateliers RHYAD

Les ateliers RHYAD constituent le principal outil de concertation, de validation et d'aide a la decision du projet.

Ils permettent :

- de recueillir les besoins du Maitre d'Ouvrage ;
- de consolider les exigences fonctionnelles ;
- de coordonner les disciplines ;
- de valider les hypotheses de conception ;
- de preparer les decisions du projet ;
- d'identifier les risques et les interfaces.

Les principaux ateliers sont :

- Atelier de lancement ;
- Atelier fonctionnel ;
- Atelier technique ;
- Atelier Design Drivers ;
- Atelier d'analyse des variantes ;
- Atelier de validation des Design Basis ;
- Revues APS ;
- Revues APD ;
- Revues PRO.

Chaque atelier fait l'objet :

- d'un ordre du jour ;
- d'un support de presentation si necessaire ;
- d'un compte rendu ;
- d'une liste d'actions ;
- d'une mise a jour des decisions et des risques lorsque cela est applicable.

Les conclusions des ateliers alimentent directement les documents du referentiel RHYAD.

# 15. Cycle de validation documentaire

Chaque document suit le cycle documentaire suivant :

**Draft → Review → Validated → Published → Obsolete**

Chaque changement de statut est associe a une validation formelle.

Les principaux statuts sont definis comme suit :

| Statut | Description |
|---|---|
| Draft | Document en cours de redaction. |
| Review | Document soumis a revue. |
| Validated | Document valide pour utilisation dans le projet. |
| Published | Document officiellement diffuse. |
| Obsolete | Document remplace ou retire de l'utilisation. |

Toute evolution entraine :

- une mise a jour de l'historique des revisions ;
- une verification des impacts documentaires ;
- une mise a jour eventuelle des documents lies.

# 16. Roles et responsabilites

| Acteur | Responsabilites |
|---|---|
| Maitre d'Ouvrage (CEVA) | Validation des besoins, arbitrages, validation des ponderations, decisions strategiques. |
| AMO / RHYAD | Animation des ateliers, redaction des livrables, coordination documentaire, gestion des interfaces, aide a la decision. |
| Maitrise d'Oeuvre / Bureaux d'Etudes | Conception technique, analyses, justification des solutions, production des etudes. |
| Entreprises | Realisation des travaux, essais, mise en service et DOE. |

Les responsabilites de chaque acteur sont precisees dans les documents contractuels du projet.

# 17. Regles d'evolution de la methode

La methode RHYAD constitue un referentiel vivant.

Toute evolution :

- est enregistree dans le Registre des Decisions ;
- est versionnee ;
- est documentee ;
- est approuvee avant sa diffusion ;
- ne remet pas en cause les versions utilisees sur les projets deja engages.

Les evolutions de la methode ont pour objectif :

- l'amelioration continue ;
- la capitalisation du retour d'experience ;
- l'harmonisation des pratiques ;
- l'amelioration de la qualite documentaire.

# 18. Principes fondamentaux RHYAD

La methode RHYAD repose notamment sur les principes suivants :

- Concevoir pour l'ensemble du cycle de vie de l'installation et non uniquement pour la reception des travaux.
- Integrer la maintenabilite des les premieres phases de conception.
- Concevoir des installations evolutives et resilientes.
- Etudier systematiquement les variantes lorsqu'elles apportent une valeur au projet.
- Justifier objectivement chaque choix technique.
- Garantir la coherence documentaire et la tracabilite des decisions.
- Privilegier des solutions simples, robustes et adaptees au contexte local.
- Limiter les consommations de ressources sans compromettre les performances pharmaceutiques.
- Integrer les exigences reglementaires des les premieres phases du projet.
- Assurer une coordination permanente entre les disciplines.
- Considerer les impacts documentaires comme une composante de chaque decision technique.

Ces principes constituent le socle methodologique commun applicable a l'ensemble des projets realises selon la methode RHYAD.

# 19. Conclusion

La methode RHYAD fournit un cadre documentaire, methodologique et decisionnel destine a conduire des projets industriels complexes de maniere coherente, tracable et collaborative.

Elle garantit :

- une gouvernance documentaire unique ;
- une continuite entre la programmation, la conception et la realisation ;
- une justification des choix techniques ;
- une aide a la decision pour le Maitre d'Ouvrage ;
- une maitrise des interfaces entre disciplines ;
- une meilleure gestion des risques ;
- une coherence documentaire sur l'ensemble du cycle de vie du projet ;
- une capitalisation des connaissances pour les futurs projets.

La methode RHYAD constitue ainsi un referentiel commun permettant d'ameliorer la qualite des etudes, de securiser les decisions et de faciliter le pilotage des projets industriels complexes.
